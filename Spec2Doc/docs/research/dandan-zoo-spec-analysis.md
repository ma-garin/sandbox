## 4. 粒度の特徴（テスト条件を推測なしに導ける根拠）

1. **機能ごとに一意な機能ID**（EH-xxx, EG-xxx, EK-xxx, Zn-xxx, W-xxx）が振られ、要求文・画面説明・データ連携仕様が同一IDで相互参照できる。テストケースの追跡単位がID一致で機械的に決まる。
2. **画面IDと遷移先が個別に明記**される（例:「支払いへすすむ」ボタンを押下時、S-005-01に遷移）。分岐網羅のためのテスト条件（画面遷移組合せ）を仕様書内の遷移記述だけで導出できる。
3. **入力項目ごとに文字種・文字数上限・境界値が数値で明記**（256文字、257文字以降不可、7文字以内の半角数字等）。境界値分析のテストケースがそのまま導ける。
4. **正常系だけでなく異常系（NG）画面が別画面IDとして独立定義**される（S-005-07カードNG、S-005-11 QRコード種別NG等）。異常系テストの網羅リストが画面一覧表から直接得られる。
5. **時刻・数値の具体例が本文中に併記**される（例:「10:05は10:00〜10:30の枠に含まれており、10:05の30分後は10:30〜11:00の枠に含まれる」71:221-251）。境界の解釈が仕様書だけで一意に決まり、テスト設計者の解釈揺れを排除している。
6. **エラーメッセージがエラーID・条件・文言の3点セットで表化**され、エラー文言一覧（21）に集約。UI表示テストの期待値がそのまま定まる。
7. **状態遷移が明示的な状態名（未使用/使用済/無効）と遷移契機で記述**され、状態ごとの許容操作が推測を要さない。
8. **通信仕様が方向・タイミング・データ内容・応答の4項目で定型化**（72章①〜⑦）。結合テストの入出力条件がこの型から機械的に抽出できる。
9. **数値パラメータに「現在の値」と「変更可能性」が併記**される（例:「残数アイコン切替閾値は変更可能であるが、現在は10枚とする」11:312-313）。テスト対象がハードコード値でなく設定値であることが明示され、パラメータ化テストの根拠になる。
10. **改版履歴が変更箇所を章単位で追跡可能な形で記述**（「Z1-202いますぐ入場券残数表示の記載を変更」等）。差分リグレッションテストの対象箇所が改版履歴から直接特定できる。

## 5. ソースコードから復元できる要素 / できない要素（見立て）

以下はすべて**見立て**（未検証）。

### 復元できると考えられる要素（見立て）
- 画面ID・画面遷移・入力項目の種類（テキストフィールド/ドロップダウン等）: UIコンポーネントのソース（フォーム定義、ルーティング定義）から静的解析で抽出可能と考えられる。
- 入力値の文字数制限・文字種制限: バリデーションロジック（正規表現、maxlengthなど）から抽出可能と考えられる。
- エラーメッセージ文言とエラーID: メッセージ定数・i18nリソースファイルから抽出可能と考えられる。
- データ項目定義・レコードレイアウト（QRコードの構成、購入情報のフィールド）: データモデル定義（DBスキーマ、DTOクラス）から抽出可能と考えられる。
- 通信インターフェースのデータ内容: APIのリクエスト/レスポンス型定義から抽出可能と考えられる。
- 状態遷移（未使用/使用済/無効）: enum定義とその遷移箇所（if/switch文）から抽出可能と考えられる。
- 非機能の数値（タイムアウト秒数、リトライ回数3回など）: 設定値・定数から抽出可能と考えられる。

### 復元が困難と考えられる要素（見立て）
- **業務背景・開発の経緯**（01の「開発背景」章、感染症対応や補助金申請の文脈）: ソースコードには一切残らない情報であり、復元不能と考えられる。
- **テスト設計スコープや重点確認事項の指定**（01の「今回のテスト設計にあたっての考慮事項」）: これは人間が意思決定した運用方針であり、コードから逆算できない。
- **団体予約や事務所運用など、システム外の業務ルール**（02:279-285「団体予約購入は電子メールまたは電話でのやりとり」）: システム対象外の運用手順であり、そもそもコード化されていない可能性が高い。
- **画面部品の意味的な説明文（「〜を促すメッセージ」等の意図の言語化）**: コード上はラベル文字列があっても、なぜその文言が選ばれたか、どのような利用者体験を意図しているかという設計意図はコードから読み取れないと考えられる。
- **時間枠の考え方の背景**（「両方の枠で入れるようにした」71:352-356 という設計意図の説明文）: 実装上のロジックは復元できても、「なぜそう実装したか」という意図はコードに残らないことが多いと考えられる。
- **改版履歴の変更理由**（「入場制限者数を倍にした」等の背景）: git logやコミットメッセージがあれば部分的に復元可能かもしれないが、確度は低いと考えられる。
- **他文書との参照関係・文書体系そのもの**（「別紙『入場券仕様書』参照」等の相互参照構造）: これは文書設計上の構造であり、コードにはそのような参照構造の対応物がないことが多いと考えられる。
- **数値の妥当性根拠**（残数アイコン切替閾値がなぜ10なのか等）: 設定値そのものは復元できるが、その数値を選んだ理由は復元不能と考えられる。
