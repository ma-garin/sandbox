### RFD-001 目的と生成ドキュメントの品質水準

#### 背景・課題
モダナイゼーション・マイグレーション案件では、現行システムの仕様書が失われている・実装と食い違っていることが多い。
移行先の設計とテスト（現新比較）の基準となる「いま動いている仕様」を、ソースコードから復元する手段が要る。

#### 決定
- 採用: GitHub リポジトリ・ローカルフォルダ・ソースファイルを入力に、リバースエンジニアリングで仕様書などの各種ドキュメントを生成する
- 品質水準: 生成される仕様書は「テスト設計コンテスト（ASTER）Open クラスの題材仕様書（だんだん動物園・話題沸騰ポット）」と同等を目標とする（2026-09-25 追加指示）。
  = テスト設計者が推測なしにテスト条件を導ける粒度（機能一覧・画面／入出力項目・業務ルール／計算式・入力値の範囲／境界・状態と状態遷移・エラー／例外時の振る舞い・用語定義）
- 両題材の具体的な章構成は一次資料で確認していない（未検証）。章構成を真似るのではなく、上の 7 観点で要件化する

#### スコープ外
- 移行そのもの（コード変換・移行先コードの生成）

### RFD-002 解析方式

#### 決定
- 採用: 静的解析と LLM の併用。構造は静的解析で事実として抽出し、業務ロジックの説明文を LLM が書く
- 出力では事実（静的解析で根拠位置あり）と推測（LLM が書いた文）を区別して明示する
- 却下: LLM のみ（事実と推測が混ざり、テストベースとして使えない）／静的解析のみ（業務の意味の説明が書けない）

### RFD-003 対象言語と実装順

#### 決定
- 対象言語: Java / COBOL / C#・VB.NET / Python / JavaScript / TypeScript / PHP / HTML / CSS
- 実装順: Web 系（JavaScript / TypeScript / HTML / CSS）を先行。他の言語は解析器の差し替えで拡張する
- 帰結: 解析器と文書生成器の間に、言語に依存しない中間表現を置く
