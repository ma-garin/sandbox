# docready-triage

社内文書をAIエージェントに渡す前に、**「そのまま変換していいか」を判定する**ツール。
判定に加えて、AIに添える構造説明文と、エージェントが最初に読む索引（目次）を生成する。

単一HTMLで動く。`docready-triage.html` をブラウザで開くだけ。
インストールもビルドもサーバーも不要。

---

## なぜ必要か — Markdown変換の何が危険か

「ExcelやPDFを `.md` に変換すればAIが読みやすくなる」という説は広く言われているが、
**実証研究では支持されていない。**

### 1. Markdownは結合セルと階層ヘッダを表現できない

GitHub Flavored Markdown の表記法には `colspan` / `rowspan` に相当する記法が存在しない。
つまり結合セルや多階層ヘッダを持つ表は、**変換した時点で必ず構造が失われる。**
これは精度の問題ではなく仕様上の事実であり、変換器を良くしても解決しない。

### 2. 「Markdownが最良の入力形式」を示した統制実験は無い

学術研究の結論は「単一の最適形式は存在せず、モデルごとに異なる」である。
同じ MMLU で、GPT-3.5-turbo は JSON 59.7% 対 Markdown 50.0% と JSON が勝ち、
GPT-4 は Markdown 81.2% 対 JSON 73.9% と逆転する（arXiv:2411.10541）。
Markdown を選ぶ理由があるとすれば「AIが読みやすいから」ではなく、
構造を表現でき、記法が冗長でなく、人間もレビューでき、既存ツールが出力できる
**最大公約数**として消去法で選ぶ、という位置づけになる。

### 3. 消える情報は、後工程では取り戻せない

OHRBench（ICCV 2025）は、書式に起因する劣化（Formatting Noise）と
内容の欠落に起因する劣化（Semantic Noise）を分けて測っている。
前者はモデルが強くなるほど耐性が上がるが、**後者は誰も免れない。**
さらに「密検索の理解力は OCR ノイズへの耐性を与えない」とされ、
検索や生成の工夫では埋め合わせられないことが示されている。

**このツールは変換を最適化するものではない。**
情報が消える変換を渡す前に見つけて止めるための、足切りである。

## できること

| タブ | 内容 |
|---|---|
| 判定する | 種別とチェック項目から `ok` / `warn` / `risk` の3段階を判定し、対処とAIに添える説明文を出す |
| 文書棚卸し | 判定した文書を一覧で持つ。CSV・タブ区切りの貼り付けで一括登録できる |
| 索引を出力 | 棚卸しから索引を生成する。Markdown（人も読める）と JSON（プログラムで読む）の2形式 |
| 根拠 | 判定ルールと出典の対応表。ルール定義から自動生成している |

## 使い方

1. `docready-triage.html` をブラウザで開く
2. **判定する** — 文書名と種別を入れ、あてはまる項目にチェックする。判定はその場で変わる
3. **この文書を棚卸しに追加** を押す（複数あるときは「文書棚卸し」タブの「まとめて登録」に貼り付ける）
4. **索引を出力** — 出力をファイルに保存し、AIに渡すフォルダの先頭に置く
5. 判定が `risk` の文書は変換せず、元の形式のまま渡す

### 状態の保存

**画面を閉じると入力は消える。** ブラウザストレージ（localStorage 等）は使っていない。
残したいときは「文書棚卸し」タブの **JSONで保存** でファイルを手元に置き、
次に開いたときに **JSONを読み込む** で戻す。

### まとめて登録の書き方

Excel やスプレッドシートの範囲をコピーして貼り付ける（タブ区切り・CSV どちらも可）。

| 文書名 | 種別 | 保管場所 | 担当 | 該当項目 |
|---|---|---|---|---|
| 2026年度 案件管理表 | Excel（表・帳票） | 共有ドライブ/営業部/管理 | 営業企画部 | セルを結合して見せている箇所がある;見出しが2段以上ある（大分類の下に小分類が並ぶ） |

- 1行目は見出し行として扱う。順番は入れ替えてよい。見出し行が無ければ左から上記の順で読む
- 種別は「エクセル」「パワポ」のような書き方でも拾う。`PDF` だけの場合は「文字をコピーできる」側として扱い、その旨を警告に出す
- 該当項目は **`;` で区切る**（項目名に `、` が含まれるため、`、` は区切りに使えない）
- 登録前に読み取り結果のプレビューが出る。読み替えた行は黄色で表示される

## 判定の考え方

種別によって、起こりうるチェック項目だけを表示する。
チェックした項目の重みを合計し、次のように3段階へ分類する。

- 重み **4** の項目が1つでも該当 → **risk（そのまま変換しない）**
- 該当しない場合、重み合計が **5** 以上 → **warn（注意して変換する）**
- それ未満 → **ok（そのまま変換してよい）**

合計点で `risk` を上書きしないのは、このツールが最適化ではなく足切りを目的とするため。
1つでも情報が消える要因があれば、他が綺麗でも変換してはいけない。

重みは効果量そのものではなく、次の基準で決めた**序数尺度**である。

| 重み | 意味 |
|---|---|
| 4 | 情報が消えること自体が構造的に確定しているか、実証研究で20pt以上あるいは相対50%以上の劣化が報告されている |
| 3 | 実証研究で10〜30pt程度の差、あるいは相対20〜50%の劣化が報告されている |
| 2 | 実証されているが効果量が小さい、または効果が間接的 |
| 1 | 定性的な品質次元として提示されているのみで、効果量が測られていない |

> **この分類方法自体は設計判断であり、実証研究に基づくものではない。**
> 投入前のコーパス品質を測る枠組みは現時点で確立しておらず、スコアの妥当性検証も行っていない。

## 判定ルールと根拠

全17項目。**根拠のないルールは入れていない。**
ツール内の「根拠」タブは、この対応表をルール定義から自動生成している（二重管理をしない）。

| # | チェック項目 | 重み | 主な根拠 | 出典 |
|---|---|---|---|---|
| 1 | セルを結合して見せている箇所がある | 4 | Markdown に colspan/rowspan が無く、変換時に必ず失われる | GFM Spec / arXiv:2604.04948 |
| 2 | 見出しが2段以上ある（階層ヘッダ） | 4 | 同上。構造保持型の変換は正答率 86.2% → 94.1% | GFM Spec / arXiv:2604.04948 |
| 3 | 列が多い（20列以上など） | 4 | 50行×5列 0.81 に対し 5行×50列 0.43。列方向は行方向より危険 | arXiv:2506.05587 |
| 4 | 行が非常に多い（100行超） | 4 | 100行超で最大 −52pt（67.06% → 14.88%）。行単位チャンク＋ヘッダ反復が有効 | arXiv:2506.05587 / arXiv:2408.17008 |
| 5 | 表がページをまたいで続いている | 3 | 素朴なチャンキングで表ヘッダがボディから切り離され相対 −27% | arXiv:2603.08655 |
| 6 | 印刷レイアウト目的のセル配置（帳票・方眼） | 2 | Formatting Noise に相当。大型LLMでは約7%の低下に留まり逓減する | arXiv:2412.02592 |
| 7 | 打ち消し線・色・太字で意味を表している | 4 | VisualStyle は OCR精度 82.9% に対し RAG精度 52.8%（−30.1pt） | arXiv:2605.00911 |
| 8 | 文字が画像になっている | 4 | 最良のOCRでも人手構造化データ比14%以上の差。Nougat −21.6pt（−60%） | arXiv:2412.02592 |
| 9 | グラフに本文にない情報がある | 4 | チャートは GT 32.9 → MinerU 9.3（−72%）。OCRテキスト経路では救えない | arXiv:2412.02592 |

| 空白 | 文書をまたぐ参照の解決を扱った研究が確認できていない |

区分の意味は次のとおり。

- **実証** — 査読論文または効果量が公開された実験
- **事実** — 仕様上そうなっているもの（測るまでもないもの）
- **空白** — 該当する研究が確認できていないこと自体を根拠とするもの

出典の選定は、同一リポジトリの先行研究調査
（[`AI2DocFrendry/docs/RESEARCH.md`](../AI2DocFrendry/docs/RESEARCH.md) v1.0）で
「実証」と分類された一次文献に限定している。
同調査が「引用してはいけない数値」として挙げた出典は使用していない。

## このツールが主張しないこと

- Markdown が LLM にとって優れた入力形式であること
- このツールのスコアが下流タスクの精度を予測すること（妥当性検証を行っていない）
- 書式を整えれば性能が上がること
  （書式に起因する劣化は逓減するが、内容の欠落は逓減しない。本ツールは後者を扱う）

## スコープ外

- サーバーサイド実装、DB、認証
- 実際のファイル変換処理（本ツールは判定と索引生成のみ。変換は別工程）
- AI API 呼び出し
- フレームワーク導入（React / Vue 等）

## ルールを追加するとき

`docready-triage.html` の `RULES.checks` に1件足す。
`sources` は必須で、`RULES.sources` に無いIDは書けない。
「根拠」タブと判定画面の両方がこの定義から自動生成されるため、追記は1箇所で済む。

出典のない項目は追加しない。
