## 1. 章構成（見出しレベル2まで、第7版）

```
（表紙・発行履歴）
目次
1 ハードウェア構成とハードウェア要求仕様
  1.1 外観と内部構成
  1.2 操作パネル部
2 操作要求仕様
  2.1 コンセント
  2.2 蓋
  2.3 沸騰ボタン
  2.4 保温設定ボタン
  2.5 解除ボタン
  2.6 給湯ボタン
  2.7 タイマボタン
  2.8 水位メータ
3 温度制御行為
  3.1 沸騰行為
  3.2 保温行為
  3.3 温度制御行為をしない（アイドル）
4 温度制御方式
5 エラー検知
6 状態遷移
  6.1 話題沸騰ポット状態遷移図（STD）
  6.2 話題沸騰ポット状態遷移表（STM）
  6.3 沸騰行為状態遷移図
  6.4 保温行為状態遷移図
7 イベント
```

**第8版との構造差（推測を含む）**: 第8版はIEEE Std 830-1998準拠の章立て（「1. はじめに」「2. 要求仕様の一般的な説明」「3. 要求仕様の具体的な説明」「4. 変更履歴」）に組み替え、用語定義・ユーザー特性・変更履歴（トレーサビリティ表）を追加している。一方で**第8版は「6 状態遷移」の実体（STD/STM/イベント表）を本文から削除し、「【22_POT-DES】状態競合設計書」という別文書への参照1行に置き換えている**（第8版 p.24）。すなわち状態遷移とイベント定義に関しては、教材として最も明確に書かれているのは今回入手した第7版の方である。

## 2. 記述要素のカタログ（第7版の実例）

| 記述の型 | 形式 | 実例（原文引用・ページ） |
|---|---|---|
| ハードウェア構成・入出力（センサー等） | 図（外観・内部構成図）＋短文（要求番号＋【説明】のみ、理由行を省く簡潔形式） | 「水位が、このポットの許容上限を超えているかどうかを検出する。」（満水センサ pot-110-11、p.4） |
| 機能要求文（要求／理由／説明の3行組） | 文章（3行組の定型テーブル） | 「アイドルの状態で、蓋を閉じたら、水位を確認し、条件に合えば沸騰行為をする。」（pot-220、理由「蓋を閉めるという行為で加熱（沸騰）の指示をしたい。」、p.6） |
| ユーザーインタフェース仕様（ボタン・表示・ランプ・ブザー） | 図（操作パネル構成図）＋文章（タイミング条件付き） | 「保温行為中で給湯中でなければ、沸騰ボタンが100msec以上押されると、ブザーを100msec鳴らした後、保温行為を中止し、沸騰行為に遷移する。」（pot-230-11、p.6） |
| 状態と状態遷移（図） | 図（STD、状態をボックスで書きイベントを矢印ラベルにしたテキスト表現） | 「アイドル →(沸騰要求)→ 沸騰行為 →(沸騰処理完了)→ 保温行為」「エラー検知 →(エラー検知)→ エラー」（6.1 状態遷移図、p.13） |
| 状態と状態遷移（表） | 表（行＝状態、列＝イベント、セル＝遷移先または「無視」） | 「沸騰行為」の行×「エラー検知」の列 → 「エラー」（6.2 状態遷移表、p.13） |
| イベント定義 | 表（イベント名・発生事象の2列） | 「・沸騰要求　蓋センサon、沸騰ボタン押下」（7 イベント、p.14） |
| 数値条件・範囲（温度・時間） | 文章＋水温-時間の模式図 | 「サーミスタが100℃になったら、更に３分間、ヒータで加熱を続ける（ヒータをonし続ける）。」（pot-311-11、p.8） |
| 異常時・エラー時の振る舞い | 表形式の要求（要求／理由／説明）＋個別のエラー種別ごとの子要求＋模式図 | 「ヒータ制御中に一定（１分）周期で水温を検出し、目標温度よりも水温が8℃下がり、かつ前回検出した水温よりも今回検出した水温の方が低い場合、ヒータ用電源をoffして30秒間ブザーを鳴らす。」（pot-500-31、p.12） |
| 制御アルゴリズム | 文章＋数式＋模式図（ON/OFF方式とPID方式を並記） | 「⊿M = M0 - M1 = Kp (T1 - T0) + Ki (Tg - T0) + Kd (2 T1 - T0 - T2)」（4 温度制御方式、p.11） |
| 前提・制約（範囲外の明示） | 文章（章の冒頭に適用範囲を宣言） | 「２．１章〜５章は、コンセントを差し込んでいる時の要求仕様である。」（pot-210の説明、p.5） |
| 用語・略語 | 個別の脚注的定義（独立の用語集章は無い。第8版で表として新設） | 「STD」「STM」の略称のみ章タイトルに使用（6.1/6.2見出し、p.13）。正式な用語定義表は第7版には無い（第8版1.3で新設）。 |

## 3. 粒度の特徴（テスト条件を推測なしに導ける根拠）

1. **要求ごとに一意な要求番号**（`pot-xxx-yy` 形式、親要求と□付き子要求の階層）を持ち、1子要求＝1テスト条件に対応させやすい（例: pot-500-11／-21／-31 の3種のエラーが並列に採番）。
2. **数値の境界がしきい値と単位付きで明記**される（「110℃を超えた場合」「３分以上」「30秒間」「8℃下がり」「1分周期」）。曖昧語がほぼ使われない。
3. **要求・理由・説明の3行組**により、境界値の設計意図まで読める（例: 満水センサのデフォルトonの理由＝「故障時、安全側に制御したいから」、p.4）。
4. **状態遷移が図（STD）と表（STM）の二重表現**で与えられ、かつ状態ごとの子状態遷移図（沸騰行為・保温行為）まで分解されている（6.1〜6.4、p.13）。図と表が同じ情報を異なる形式で相互検証できる。
5. **イベントの発生条件が独立した表で定義**され（7章）、状態遷移表のイベント名と1対1で対応する。「沸騰要求」が「蓋センサon、沸騰ボタン押下」のどちらか一方で成立するのか両方かは、この章と関連する2.2/2.3の要求文を突き合わせて特定できる。
6. **正常・異常の停止条件が箇条書きで列挙**される（「以下のいずれかの状態となった時、沸騰行為を止める」＋3項目、pot-310-31、p.8）。AND/ORの構造が明示される。
7. **モードごとの目標温度が一覧できる形で並記**される（「高温モード:98℃」「節約モード:90℃」「ミルクモード:60℃」、pot-320-21、p.9）。
8. **初期状態・デフォルト値が個別の要求として明記**される（例: pot-210-11「コンセントを差し込むと…デフォルト値がセットされ…アイドルになる」、p.5、pot-330-11「コンセントに初めて繋いで直ぐは、一度アイドルとなる」、p.9）。
9. **章の適用範囲を冒頭で自己申告**し、範囲外の事象を明示する（「２．１章〜５章は、コンセントを差し込んでいる時の要求仕様である」、p.5）。
10. **未確定・簡略化箇所が可視化されている**（推測を含む注記）: ブザー周波数が「○○KHzの音が出る」（pot-110-22、p.4）と伏字のまま残っており、第8版で「0.88KHzの周波数、-40dBの強度」に具体化されている。「曖昧さを無くした」と序文で謳う第7版にも数値未確定箇所が残る例であり、テスト設計者が仕様のレビュー観点（数値の未決定を検出する）を訓練する教材的特徴と考えられる（推測）。

## 4. ソースコードから復元できる要素／できない要素（見立て）

**復元できる可能性が高い（推測）**:
- 数値しきい値・境界条件（110℃、98℃、8℃、30秒、3分、モードごとの目標温度98/90/60℃等）— 定数・比較式から機械的に抽出可能。
- 状態遷移表（STM）そのもの — 状態変数と条件分岐（if/switch、あるいは状態機械ライブラリの遷移テーブル定義）から、状態×イベント→遷移先の対応表として復元しやすい。第7版がこの表を明示的な形式で持っていることは、Spec2Doc の出力フォーマットの目標として直接参考にできる。
- イベント発生条件（「蓋センサon、沸騰ボタン押下」等）— センサ入力・ボタン入力を扱うコード箇所から復元可能。
- UI表示・ランプ点灯条件、ブザー鳴動条件とその継続時間 — 出力制御コードの分岐・タイマ値から復元可能。
- 制御アルゴリズムの定数（比例・積分・微分係数、制御周期）— コード中の定数として存在すれば復元可能。ただし数式そのもの（PID方式である、という設計選択の説明文）はコードのロジックからアルゴリズムの型を推定できても、なぜその方式を選んだかの理由は別。

**復元が困難、または別途の情報源が必要（推測）**:
- 各要求の「理由」欄（なぜ安全側デフォルトにするか、なぜ3秒待つか等の設計意図）— コードのコメントに残らない限り復元不可能。ドメイン知識・要件文書が必要。
- 状態遷移図（STD、視覚的な図表現）そのもの — 状態機械コードから状態と遷移の集合は復元できるが、教育的に見やすい図としてのレイアウト・グルーピング（沸騰行為状態遷移図・保温行為状態遷移図のような粒度分割）は人間の設計判断であり、機械的に同じ粒度分割を再現できるとは限らない。
- 「○○章はコンセントを差し込んでいる時の要求仕様である」のような**適用範囲の自己申告**（p.5）— コードの構造からは、ある関数群が「特定の前提条件下でのみ有効」であることを明示的に知ることは難しい（コメントかテストケースが無い限り）。
- ユーザーの安全確保のための理由づけ（「安全確保のため」pot-221理由、p.6）等の**安全要求の意図** — 規制・品質保証プロセスに基づく判断であり、コードには現れない。
- 版を重ねた曖昧さの解消履歴（例: ブザー周波数が第7版「○○KHz」→第8版「0.88KHz」に確定した経緯）— レビュープロセスの記録であり、単一時点のソースコードからは再構築できない。

**留意点（未検証）**: 上記の切り分けは仕様書の記述とテスト設計・要求工学の一般知識に基づく見立てであり、GOMA-1015の実ソースコード（非公開、本分析では未入手）を用いた実証は行っていない。Spec2Doc要件化にあたっては、この見立てをコード解析パイロットで検証する工程を別途置くことを推奨する。
