## 目的・ゴール

- 目的: ソースコード（GitHub リポジトリ・ローカルフォルダ・ファイル）からリバースエンジニアリングで仕様書などの各種ドキュメントを生成し、モダナイゼーション・マイグレーションの設計とテストの基準にする（RFD-001）
- ゴール: 生成仕様書の水準を **ASTER テスト設計コンテスト Open クラスの題材仕様書（だんだん動物園・話題沸騰ポット）と同等** にする。
  すなわち、テスト設計者が生成仕様書だけを入力に、推測なしにテスト条件を導けること
- 第 1 リリースの完了定義（RFD-007）: 利用者が Web 画面で GitHub の URL・.zip・フォルダのどれかを渡すと、Spec2Doc が D01〜D09・D11・D12 を生成し、画面で閲覧でき、4 形式でダウンロードできること。Web システムを主な利用形態とし、CLI は同じ中核を呼ぶ補助の形態とする
- 水準の根拠（一次資料の分析。本書では章構成・粒度を推測で書かない）:
  - だんだん動物園 9 文書: `docs/research/dandan-zoo-spec-analysis.md`（§1 文書体系・§3 記述要素のカタログ・§4 粒度の特徴・§5 復元できる要素／できない要素）
  - 話題沸騰ポット 第 8 版: `docs/research/pot-spec-analysis.md`（§1 章構成（IEEE 830 準拠）・§2 記述要素のカタログ・§3 粒度の特徴・§4 復元できる要素／できない要素）
- 本書で「テストベース 7 観点」と呼ぶもの（`docs/research/dandan-zoo-spec-analysis.md` §3・§4 の記述要素を 7 つに束ねた呼び名。束ね方は本書の定義）:
  1. 機能一覧（機能 ID 付き。§4-1） 2. 画面・入出力項目（画面 ID・画面部品表・遷移先。§4-2） 3. 業務ルール・計算式（§3 料金計算式）
  4. 入力値の範囲・境界（文字種・上限・具体例。§4-3・§4-5） 5. 状態と状態遷移（状態名・契機・許容操作。§4-7）
  6. エラー・例外時の振る舞い（エラー ID・条件・文言。§4-4・§4-6） 7. 用語定義（§3 用語定義）
  - ポットから足す粒度（pot §3）: 要求番号の階層（§3-1）、数値の境界に閾値と単位（§3-2）、分岐条件の AND/OR を列挙で明示（§3-4）、既定値と初期状態を個別に明記（§3-7）、「無い」と「未記載」を区別（§3-9）
- ソースから復元できない要素（業務背景・設計意図・数値の選定理由・各要求の「理由」欄・ユーザー特性・適用範囲の宣言。dandan §5・pot §4）は、生成仕様書に事実として書かず D09 確認事項一覧へ回す
- 以下の要件で「dandan」は dandan-zoo-spec-analysis.md、「pot」は pot-spec-analysis.md を指す。両ファイルの「復元できる／できない」は見立て（未検証）であり、第 1 リリースの受入テスト（REQ-N-006・REQ-N-007）で検証する

## 生成ドキュメントの種類とリリース範囲

## スコープ / 対象外

- スコープ（第 1 リリース）: Web 系 4 言語（JavaScript / TypeScript / HTML / CSS）の解析、D01〜D09・D11・D12、4 形式の出力、Web 画面（主）と CLI（補助）
- 評価用システム: 受入テスト（REQ-N-006・REQ-N-007）の入力として、第 1 リリースの受入テスト準備で用意する（Spec2Doc 本体の機能ではない）。Q-08 の回答 C（A と B の両方）で確定。A の動物園の既存実装は実在が未確認で、無ければ B のポットの JS 新規実装だけで評価する
- 対象外（Won't）:
  - 移行そのもの（移行先コードの生成・コード変換）
  - 動的解析（対象プログラムの実行・トレース取得）。解析対象のコードは実行しない
  - 第 1 リリースでの Web 系以外の言語の解析器（中間表現の拡張点だけは第 1 リリースで作る）
  - 本番データベースへの接続・実データの参照
  - 生成文書を手で直した内容の再取り込み（ラウンドトリップ編集）
  - 複数人の同時利用・利用者認証・定時実行・CI からの自動起動
